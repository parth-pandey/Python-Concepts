## Class & Object

### Class
A **blueprint** for creating objects. Defines structure (attributes) and behavior (methods).

```python
class Car:
    wheels = 4  # Class variable (shared by all objects)
    
    def __init__(self, brand, model):  # Constructor
        self.brand = brand  # Instance variable
        self.model = model
    
    def drive(self):  # Instance method
        print(f"{self.brand} is driving")
```

### Object
An **instance** of a class. Contains actual data.

```python
car1 = Car("Toyota", "Camry")
car2 = Car("Honda", "Civic")

car1.drive()  # Toyota is driving
```

### Key Points
- `self` refers to the current object (convention, not keyword)
- `__init__` is the constructor, called automatically when object is created
- Class variables are shared; instance variables are object-specific

## Encapsulation

**Bundling data and methods together** + **controlling access** to internal state.

### Access Levels (by convention)

```python
class BankAccount:
    def __init__(self, balance):
        self.balance = balance        # Public
        self._account_id = "12345"    # Protected (internal use)
        self.__pin = 1234              # Private (name mangling)
    
    def get_pin(self):                 # Getter method
        return self.__pin
    
    def set_pin(self, new_pin):        # Setter method
        if len(str(new_pin)) == 4:
            self.__pin = new_pin
```

### Access Outside Class

```python
acc = BankAccount(1000)
print(acc.balance)           # ✅ Works (public)
print(acc._account_id)       # ⚠️ Works but discouraged
print(acc.__pin)             # ❌ Error
print(acc._BankAccount__pin) # ✅ Works (name mangling bypass)
```

### Interview Points
- Python has **no true private** - uses conventions
- `__var` becomes `_ClassName__var` (name mangling)
- Use getters/setters to control access and add validation
- **Why encapsulate?** Protects data integrity, allows change of internal implementation without breaking external code

## Inheritance

One class **inherits** properties and methods from another.

### Types of Inheritance

#### 1. Single Inheritance
```python
class Animal:
    def eat(self):
        print("Eating")

class Dog(Animal):
    def bark(self):
        print("Barking")

dog = Dog()
dog.eat()   # Inherited from Animal
dog.bark()  # Own method
```

#### 2. Multiple Inheritance
```python
class Father:
    def skills(self):
        print("Cooking")

class Mother:
    def skills(self):
        print("Dancing")

class Child(Father, Mother):  # MRO: Child → Father → Mother
    pass

c = Child()
c.skills()  # Cooking (Father's method called first)
```

#### 3. Multilevel Inheritance
```python
class Grandparent:
    def heritage(self):
        print("Family wealth")

class Parent(Grandparent):
    def house(self):
        print("House")

class Child(Parent):
    pass

c = Child()
c.heritage()  # From Grandparent
c.house()     # From Parent
```

### Using `super()`

```python
class Animal:
    def __init__(self, name):
        self.name = name

class Dog(Animal):
    def __init__(self, name, breed):
        super().__init__(name)  # Call parent constructor
        self.breed = breed
```

### Interview Points
- **MRO (Method Resolution Order)**: Left to right, depth-first
- `super()` calls parent class method
- Multiple inheritance can cause **diamond problem** (use with caution)
- Check MRO: `ClassName.__mro__` or `ClassName.mro()`

## Polymorphism

**Same interface, different implementations**. Same method name behaves differently for different objects.

### Method Overriding

```python
class Animal:
    def speak(self):
        print("Animal sound")

class Dog(Animal):
    def speak(self):  # Overriding parent method
        print("Bark")

class Cat(Animal):
    def speak(self):
        print("Meow")

# Polymorphism in action
animals = [Dog(), Cat(), Animal()]
for animal in animals:
    animal.speak()  # Different output for each
```

### Duck Typing (Python's approach)

```python
class Duck:
    def swim(self):
        print("Duck swimming")

class Fish:
    def swim(self):
        print("Fish swimming")

def make_it_swim(obj):
    obj.swim()  # Don't care about type, just that it has swim()

make_it_swim(Duck())  # Works
make_it_swim(Fish())  # Works
```

### Operator Overloading

```python
class Point:
    def __init__(self, x, y):
        self.x = x
        self.y = y
    
    def __add__(self, other):  # Overload + operator
        return Point(self.x + other.x, self.y + other.y)
    
    def __str__(self):  # Overload print()
        return f"({self.x}, {self.y})"

p1 = Point(1, 2)
p2 = Point(3, 4)
p3 = p1 + p2  # Uses __add__
print(p3)     # Uses __str__ → (4, 6)
```

### Interview Points
- **Runtime polymorphism** (method overriding) vs **Compile-time** (not in Python)
- Python uses **duck typing**: "If it walks like a duck and quacks like a duck, it's a duck"
- No method overloading like Java (last definition wins)
- Can use `*args` or default parameters for variable arguments

## Abstraction

**Hiding implementation details**, exposing only what's necessary. Defines "what to do" not "how to do".

### Abstract Base Class (ABC)

```python
from abc import ABC, abstractmethod

class Shape(ABC):  # Cannot instantiate this
    @abstractmethod
    def area(self):
        pass  # Must be implemented by child
    
    @abstractmethod
    def perimeter(self):
        pass

class Rectangle(Shape):
    def __init__(self, width, height):
        self.width = width
        self.height = height
    
    def area(self):  # Must implement
        return self.width * self.height
    
    def perimeter(self):  # Must implement
        return 2 * (self.width + self.height)

# shape = Shape()  # ❌ TypeError: Can't instantiate abstract class
rect = Rectangle(5, 10)  # ✅ Works
```

### Why Use ABC?

```python
class Circle(Shape):
    def __init__(self, radius):
        self.radius = radius
    
    def area(self):
        return 3.14 * self.radius ** 2
    # Forgot perimeter!

# circle = Circle(5)  # ❌ Error at instantiation, not runtime
```

### Interview Points
- **Abstraction vs Encapsulation**: Abstraction = design level (what to show), Encapsulation = implementation level (how to hide)
- ABC enforces a **contract** - child must implement abstract methods
- Without ABC, missing methods only error when called (runtime)
- Use when you want to define a common interface for different classes

## Key Differences

### Abstraction vs Encapsulation

| Abstraction | Encapsulation |
|-------------|---------------|
| Hides **complexity** | Hides **data** |
| Design level (interface) | Implementation level (access control) |
| What to expose | How to protect |
| Uses abstract classes | Uses access modifiers (public, private) |
| "Here's what a car can do" | "You can't directly access the engine" |

### Polymorphism vs Abstraction

| Polymorphism | Abstraction |
|--------------|-------------|
| Same method, **different behavior** | Defines **what** must exist |
| Implementation focused | Contract focused |
| About using objects interchangeably | About defining interfaces |
| Example: `dog.speak()` vs `cat.speak()` | Example: All shapes must have `area()` |

### Class Variable vs Instance Variable

```python
class Student:
    school = "ABC School"  # Class variable (shared)
    
    def __init__(self, name):
        self.name = name  # Instance variable (unique per object)

s1 = Student("Alice")
s2 = Student("Bob")

print(s1.school)  # ABC School (same for all)
print(s2.school)  # ABC School

Student.school = "XYZ School"  # Changes for all
print(s1.school)  # XYZ School
print(s2.school)  # XYZ School

s1.name = "Alicia"  # Only changes s1
print(s2.name)  # Still Bob
```

## Quick Interview Points

### Method Types

```python
class Demo:
    class_var = "shared"
    
    def instance_method(self):
        # Access: self.class_var, self.instance_var
        return "Needs object"
    
    @classmethod
    def class_method(cls):
        # Access: cls.class_var
        return "Needs class"
    
    @staticmethod
    def static_method():
        # Access: nothing specific
        return "Independent utility"
```

### Common Dunder (Magic) Methods

```python
__init__    # Constructor
__str__     # print(obj)
__repr__    # obj representation
__len__     # len(obj)
__add__     # obj1 + obj2
__eq__      # obj1 == obj2
__lt__      # obj1 < obj2
__getitem__ # obj[key]
__call__    # obj()
```

### MRO (Method Resolution Order)

```python
class A:
    def show(self):
        print("A")

class B(A):
    pass

class C(A):
    def show(self):
        print("C")

class D(B, C):
    pass

d = D()
d.show()  # Output: C
print(D.__mro__)  # D → B → C → A → object
```

### Common Interview Questions

**Q: What are the 4 pillars of OOP?**
A: Encapsulation, Abstraction, Inheritance, Polymorphism

**Q: Difference between `__init__` and `__new__`?**
A: `__new__` creates the object, `__init__` initializes it. `__new__` is rarely overridden.

**Q: Can you access private variables from outside?**
A: Yes, using name mangling: `_ClassName__variable`

**Q: What is monkey patching?**
A: Modifying class/module at runtime
```python
class A:
    def show(self):
        print("Original")

A.show = lambda self: print("Patched")  # Monkey patching
```

**Q: What is the diamond problem?**
A: Multiple inheritance where two parent classes inherit from same grandparent. Solved by MRO.

**Q: Does Python support method overloading?**
A: No traditional overloading. Use default arguments or `*args/**kwargs`.

## When NOT to Use OOP

- Simple scripts or one-off tasks
- When functions alone are clearer
- Over-engineering small problems
- When performance is critical (function calls faster than methods)

**Remember**: OOP is a tool, not a requirement. Use when it adds clarity, not complexity.
